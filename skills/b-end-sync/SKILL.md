# 展示站与 B 端 Skill 同步维护

目标：用户修改 `b-end-showcase` 中的模块或业务页面时，同步维护 `b-end-page` 中对应的可复用设计知识。一个提交里有两端文件不等于它们已经一致；不能只更新版本号或文件摘要便宣布同步成功。

## 先定位再修改

1. 定位同时包含 `b-end-showcase/` 与 `b-end-page/` 的仓库。可从工作目录向上查找；脚本支持 `--repo`。不依赖用户机器的固定绝对路径。
2. 首次在该仓库工作，读 [结构与同步边界](references/architecture.md)。按模块 ID 或页面路由查 [文件映射](references/file-map.json)，并核对实时路由、注册表及 import 依赖。映射是导航资料，不能覆盖当前代码事实。
3. 运行 `python3 <本Skill目录>/scripts/sync_check.py audit --repo <仓库> --scope <范围>`。范围例：`Form9`、`G-4`、`page:/form/basic`、`page:/examples/store-operations`、`theme`、`shell`。省略 scope 检查全部。退出码 1 表示未核验/漂移/已知阻塞，不是脚本故障；2 才是执行或输入错误。
4. 读取命中范围的实际实现、CSS、`l2Modules.ts` 元数据、`designSpecs.ts` 对应条目与解析逻辑，以及 L2/L1 知识全文的相关章节。查找调用者，不能仅改预览组件。存在历史不同步时，先列明涉及本次任务的差异，按用户当前目标收敛；范围外差异保留在审计结果，不顺手替换所有旧规范。

## 同步规则

- **模块改动**：更新真实预览/复用组件、CSS、受影响业务页、目录描述/变体、复制 Spec 和对应 L2 的布局、输入、状态、事件、约束、MTD 实现及代码骨架。新增变体要核对预览显示名与 `getDesignSpec(id, variantName)` 的解析结果，避免退回“全部变体”而伪装成当前变体规范。
- **页面改动**：沿 `App.tsx` 当前路由找到真正入口及其子组件；更新该页 Design Spec（如存在）。可复用的装配决策写入对应 L1，模块内规则写 L2；筛选/选择/分页/动作联动按 `page-contract.md` 同步。业务文案、虚构门店数据与临时场景不直接变成通用规则；在证据中明确不泛化的理由。
- **主题/Token 改动**：同时核对网站 `tokens.css`、ThemeProvider、图表 token、复制 Spec 内嵌 token 表，和 Skill `style-profile.md`、`theme-system.md`、`theme-examples/*`。保持蓝/黄两个主题可用，嵌入案例的主题联动也须验证。
- **外壳改动**：ShowcaseLayout、目录搜索、文档卡片、iframe 展示等属于知识库展示方式。只记录“外壳例外”及理由，不把灰白展示站样式、双侧栏或 iframe 写入业务页面生成规范。若同时改变了业务组件规范，按模块或主题流程同步那一部分。
- 新增、删除、换号、改路由或迁移入口，先更新 `references/file-map.json`，再核验索引/注册/复制 Spec/调用者。不能将旧 F/DT/D 别名当作当前规范 ID。
- 遵守 `module-contract.md` 与 `page-contract.md`。G-4、Form5、FD3 的用途不同；G-4 内置操作栏/分页，不另拼 G-5/List-2/List-3。图表 D-* 与详情 Detail* 不混用。
- MTD API 有变更时，按 `b-end-page/mtd3/MTD3-SKILL.md` 与脚本查询，不能把模块语义事件直接当组件 props。同步参考代码，不要求 Vue 示例与 React 源码逐字相同。

## 验证与记录

读 [一致性判定与证据](references/verification.md)，执行与变更相称的检查：
- 核对模块身份、实际变体、关键视觉值/Token、状态和事件，以及复制出的完整 Spec；页面同时核对组合关系。
- 执行展示站构建，浏览器验证受影响预览或业务页。交互改动操作实际控件；主题改动测蓝→黄→蓝；嵌入页面测抽屉范围与主题联动。只在有必要时增加自动化测试。已有服务供用户浏览时保留运行。
- 审计脚本仅静态读取 TS AST，不执行页面代码。文件哈希用于检测复核后的漂移；不能替代视觉与交互核验。共享文件的整文件哈希会保守地让多个范围过期，不能为了“全绿”忽略这些范围。
- 审计返回 `blocked`：修复本次范围的问题；历史其他范围的问题可以保留。`unreviewed`：尚无语义核验记录。`stale`：上次记录后代码、知识、映射或证据变化。只有语义核验完成且记录的当前指纹未漂移，才是 `verified`。
- 核验后将带当前指纹的证据 JSON 写到仓库 `.sync/evidence/`，再运行 `sync_check.py record --repo <仓库> --scope <范围> --evidence .sync/evidence/<文件>.json`。逐范围记录，不批量伪造已核验状态。用户明确只改一端时遵从并报告另一端未同步，不强行通过核验。
- 最终说明：修改了哪些展示文件和知识文件、哪些没有同步及原因、验证范围/结果、未解决差异。局部通过不能表述为全仓库同版本。

## 版本与交付边界

原始 Friday `skillhub.version`、签名/manifest、L2 索引版本和 npm package 版本不是同一个版本空间。保留原始签名来源，不重新伪造签名，不把本地修改宣称为 Friday 发布。两端当前对应关系使用 Git 提交 + 范围内容指纹 + 核验证据。创建/修改本 Skill 不自动授权提交、推送或上传 Friday；按当前用户授权执行。
