01 / PROBLEM
问题定义

组件用对了，页面仍需要设计判断

当设计师、产品和研发用一句话提出需求，组件 API 能回答“怎么实现控件”，整页的信息优先级和操作路径仍需要被明确。

比较维度第一步 · mtd3-skill第二步 · b-end-page
知识组织组件清单、API、示例与注意事项页面装配、功能模块与底层组件映射
生成判断识别组件，查询用法，再组织代码识别任务，选择骨架与模块，再落实代码
视觉约束基础色彩、间距、图标与控件规则整体布局、模块变体、容器和统一样式
验证范围组件使用、报错与基础样式进一步检查组合合理性和跨模块反馈

建设目标：将依赖临场判断的组织经验，转化为可重复使用的设计规则。

第一步已经支持页面生成。第二步沿用其组件能力；两者查询脚本及五份组件参考文档逐文件一致。问题判断来自规划与资产分析，尚不等同于用户研究结论。

02 / STRATEGY
策略与取舍

统一稳定结构，为任务差异保留空间

可复用的单位需要承载任务语义。相同的底层组件，可能对应完全不同的业务行为。

01 / 先判断任务

我应该先看什么，
接下来做什么？

先识别管理、分析、录入或查看，再选择页面骨架和容器。管理列表优先筛选与操作；表单组织输入与校验；详情强调只读信息层级。

设计动作
建立四类页面的 L1 装配逻辑，而非仅按业务名复制整页。

02 / 明确模块边界

同样是表格，
为什么不能直接复用？

G-4 管理表格内含工具栏和分页；Form5 支持增删行与编辑；FD3 展示只读关联记录。分别规定数据、状态和组合限制。

设计取舍
统一描述语义，保留表单、详情的专用路径，避免为了统一而丢失任务差异。

03 / 规定行为反馈

点击之后，
哪些内容应该一起变化？

相关任务补充数据源、状态、事件和动作。查询后不仅刷新表格，还要更新总数、统计和有效页码；缺少时间数据时不生成真实趋势。

设计动作
扩展 Design Spec，并用实际操作核对反馈，避免只检查按钮是否存在。

稳定部分进入规则；变化部分由任务、数据、参数与变体决定。

03 / PROCESS
知识建设流程

让设计规则从案例中生长，再回到案例中验证

Showcase 是可运行的设计知识载体：案例呈现效果，模块记录组合，规格解释依据，问题反馈推动规则修订。

01 识别缺口

定位生成问题

从规划与生成案例中区分组件错误、结构问题、视觉偏差和交互缺失。

02 打磨案例

在代码中调整

使用真实组件库构建页面，观察容器、间距和信息层级的最终效果。

03 提炼知识

沉淀 L1 与 L2

抽取骨架、模块、变体和边界，记录数据前提与底层实现映射。

04 按需生成

把依据带入代码

先选型，再读取命中规范，查询真实 API；相关任务补充状态与联动。

05 检查反馈

运行并修正规则

检查构建、视觉与操作结果，把可复现的问题回写知识库。

← 反馈回流：生成暴露的问题，成为下一轮规范的输入案例 ⇄ 规则

减少不必要的等待

列表与看板给出有依据的 Design Spec 后继续生成，将人工核对放在具体结果上。这个调整来自试用中“不要暂停等用户”的明确反馈。

控制读取与改动范围

先识别页面类型与模块清单，再读取对应知识。已有导航与状态管理优先复用；小范围样式修改不必重新描述整页。

04 / VALIDATION
案例与迭代

用真实操作检查规则是否落地

门店页 / 已完成实测查询带动关联结果变化

筛选草稿与生效条件分离；查询后重置页码，同步表格、总数和统计；零结果呈现空态。已检查分页、详情、导出与主题切换。

采购表单 / 反馈驱动修订将视觉问题追溯到规则归属

试用反馈指出外部留白偏大、分割线多余。修订明确间距只由一层负责，避免父容器、卡片与分组重复叠加。

已形成的资产

从局部用法到整页组织

在组件知识基础上，形成页面装配逻辑、模块规范、统一样式和可运行案例。近期补充行为契约，使交互联动有可核对的描述。

当前的边界

规则不等于自动保障

当前依然由模型生成代码，没有独立运行时或自动 Schema 校验器。一次实测说明链路可运行，不能代表普遍成功率或量化的效率提升。
